# myalgorithm9 -- P4 밴드(고포화) force-place 꼬리 개선

`myalgorithm8.py`를 베이스로, P4 밴드(util = 총 processing time /
(베이수 × max_due) >= 10.0)에서만 발동하는 개선 3종을 추가했다. 이
밴드는 `w1`(지각 페널티)이 다른 목적함수 항을 수십~수천 배 지배하는데,
TIME GUARD가 걸리는 순간 남은 블록 전부가 `_force_place`(빠른 정수
휴리스틱 폴백)로 넘어가고, 이 꼬리가 obj1(지각)의 대부분을 만든다는
사실이 사전 계측으로 확인되어 있었다 (prob_37 기준 꼬리가 obj1의 89%).

세 개선 모두 **util>=10 게이트 밖에서는 코드 경로가 전혀 바뀌지
않는다** — P1~P3 인스턴스는 myalgorithm8과 100% 동일하게 동작한다.

## 개선 1+2: 꼬리 순서 부분열거 (Tail Portfolio) + 접미사 국소탐색 (TailLS)

**문제:** TIME GUARD 발동 시 꼬리 블록들은 EDD 순서 하나로만, 블록당
한 번씩 `_force_place`에 그리디 커밋된다. 순서가 공간 점유 패턴을
결정하는데 열거가 전혀 없다.

**해법 (Tail Portfolio):** 꼬리를 5가지 순서로 시뮬레이션한다.

- `edd` (현행, 항상 포함 -- 회귀 방지의 기준선)
- `edd_area` -- due 동률 시 풋프린트 큰 블록 먼저
- `edd_proc` -- due 동률 시 공정시간 긴 블록 먼저
- `edd_wl` -- due 동률 시 workload 큰 블록 먼저
- `latest_start` -- (due - proc) 오름차순 (여유 없는 블록 먼저)

각 순서를 순수 정수 연산(`_force_place`)으로 시뮬레이션하고 꼬리
지각 합이 최소인 순서를 채택한다. 시뮬레이션 비용은 실측해, 추가
변형이 예산(`TAIL_PORTFOLIO_TIME_FRAC` = 93%)을 넘길 것 같으면
건너뛰고 그때까지 찾은 최선(EDD 포함)으로 커밋한다.

**해법 (TailLS):** 포트폴리오 승자 순서 위에서, 지각 기여가 큰 블록을
더 앞 위치로 당기는 이동(`pull`: 고정 4위치 / `swap`: 비지각 선행
블록과 교환, 최대 3개)을 시도한다. "순서의 j번째를 바꾸면 앞 j-1개의
배치는 그대로"라는 구조를 이용해 **접미사만 증분 재시뮬레이션**하므로
비용이 싸다. 예산은 가드 시점 잔여 시간의 50%까지만 쓴다.

**안전장치:** 두 단계 모두 엄격 개선(꼬리 지각 합 감소)일 때만 채택
-- 절대 현행보다 나빠질 수 없다.

**실측 (prob_33, 런 내부 격리 비교, wall-clock 노이즈 무관):**

| 단계 | 개선폭 |
|---|---|
| Tail Portfolio (edd_wl 승) | -9.2% |
| Tail Portfolio (다른 가드 이벤트, edd_area 승) | -8.3% |
| TailLS (포트폴리오 승자 위에 추가) | -1.1% ~ -1.4% |

이동 후보 비교(pull / pull+cluster / pull+swap, prob_33 2런/구성):
`pull+swap`이 최고(-0.89%, 채택 효율 ~7%)로 채택. `pull+cluster`는
채택 수는 많았지만(7) 개별 폭이 작아 근소한 차이로 2위.

## 개선 3: Free-space 인지 force-place (ForceBestFit)

**문제:** `_force_place`는 각 진입시각에서 bottom-left 스캔으로
"가장 먼저 찾은" disjoint 위치를 그냥 채택한다. 남는 자투리 공간이
다른 블록이 못 쓸 만큼 작게 남아도 신경 쓰지 않는다. 베이 수가 적을
때(prob_23: 2개, 64×25 / 150×23) 이런 나쁜 자투리 하나가 그 베이
전체의 활용도를 깎아먹는다.

**해법:** 같은 진입시각에서 disjoint 후보를 최대 5개(`FORCE_BESTFIT_
MAX_CAND`)까지 모으고, 각 후보의 우측/상단 gap이 "0보다 크고 인스턴스
전형적 블록 크기(전체 블록 최소변의 20th percentile,
`_MIN_BLOCK_DIM`)보다 작은" dead-sliver를 만드는지 세어, 가장 적은
후보를 채택한다. 동점이면 기존 bottom-left 순서(스캔에서 먼저 나온
것)를 유지 -- 자투리 차이가 없으면 기존 동작과 완전히 동일한 순수
첨가형 변경이다.

**실측 (prob_23, 2런):**

| 설정 | obj1 (평균) | objective |
|---|---|---|
| off | 742.5 | 10.39M |
| **on (MAX_CAND=5)** | **731 (-1.5%)** | **10.24M (-1.5%)** |

두 런이 완전히 동일한 값으로 수렴 -- free-space 인지 선택이 실행
타이밍에 덜 민감한 결정적 배치를 만드는 부수 효과도 관찰됨.

**주의 (미채택 실험):** `MAX_CAND`를 5→10으로 늘려봤더니 오히려
off와 완전히 동일한 값으로 후퇴했다. 선택 로직(엄격 부등호 tie-break)
상 후보를 더 본다고 논리적으로 나빠질 수 없으므로, 이는 후보 스캔
증가분이 소모한 wall-clock이 TIME GUARD/포트폴리오 예산 분기점을
밀어 다른 실행 경로로 캐스케이드된 것으로 추정된다 (이 코드베이스의
고질적 wall-clock 민감성, 아래 검증 원칙 참조). **MAX_CAND=5로
고정.**

## 기각된 아이디어 (참고용, 코드에 없음)

**Entry-first 스코어:** ADP(근사 동적계획법) 계열의 "지배항 중심
cost-to-go" 아이디어를 빌려, P4 밴드 배치 스코어에 `w1 * entry` 항을
더해 탐색 자체를 "entry 최소화 사전식 정렬"로 바꿔봤다. 결과: 6개
프록시(23/28/30/31/33/37) 중 4개에서 obj1 악화. entry만 우선하니
부하균형(obj2)이 크게 무너지고(예: prob_37 459→1957), 그 부작용이
후속 블록 배치의 지각까지 악화시킨 것으로 추정. **지배항 사전식
정렬은 이 문제에서 지각-부하균형 트레이드오프를 너무 거칠게 끊는다는
반례로 기록.**
